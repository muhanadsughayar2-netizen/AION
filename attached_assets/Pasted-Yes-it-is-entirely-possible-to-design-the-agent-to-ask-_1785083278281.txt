Yes, it is entirely possible to design the agent to ask questions, present choices to the user, and pause for input before proceeding. In agent architecture, this is commonly referred to as Human-in-the-Loop (HITL) automation.
By introducing an interactive tool, you can prevent the agent from getting stuck in brute-force loops when navigating complex, unpredictable interfaces like Google Docs, Gemini, or NotebookLM. Instead of failing repeatedly, the agent can pause, output a set of options, and ask you which path to take.
1. Implementing Interactive Questions and Choices
To achieve this, we can define a new tool called askUser inside the AGENT_TOOLS array. When the AI decides it needs clarification, permission, or a decision, it calls this tool. The frontend then renders interactive buttons in the chat window and pauses the agent loop until you click one.
Step A: Declare the Tool in AGENT_TOOLS
Add this tool definition to your existing AGENT_TOOLS registry:
code
JavaScript
{
  name: 'askUser',
  description: 'Pause execution and ask the user to make a choice or provide clarification. Use this when a step is ambiguous, requires permission, or when you want to suggest alternative paths.',
  parameters: {
    type: 'object',
    properties: {
      question: { 
        type: 'string', 
        description: 'The question or explanation of the choice being presented to the user.' 
      },
      options: { 
        type: 'array', 
        items: { type: 'string' }, 
        description: 'A list of explicit choices/buttons to present to the user. E.g., ["Proceed with Slide 1 outline", "Regenerate summary", "Cancel task"]' 
      },
      allowFreeText: {
        type: 'boolean',
        description: 'If true, allows the user to type a custom text response in addition to clicking the options.'
      }
    },
    required: ['question', 'options']
  }
}
Step B: Handle the Interaction in the Frontend Loop
Inside your runAgentTask loop in ai-chat (34).js, you can intercept the askUser tool call, render the options as buttons, and return your selection back to the model as a functionResponse.
Here is an architectural example of how to pause and resolve the user's choice:
code
JavaScript
// A helper to pause execution until a user clicks an option
function awaitUserChoice(question, options, allowFreeText) {
  return new Promise((resolve) => {
    const thread = document.getElementById('chatThread');
    
    // Create an interactive choice card
    const card = document.createElement('div');
    card.className = 'chat-bubble ai';
    card.style.cssText = 'background: rgba(99,102,241,0.08); border: 1px solid rgba(99,102,241,0.3); padding: 12px; border-radius: 12px; margin: 8px 0;';
    
    let buttonsHtml = options.map((opt, i) => 
      `<button class="choice-btn" data-val="${opt}" style="margin: 4px; padding: 6px 12px; background: #6366f1; color: white; border: none; border-radius: 6px; cursor: pointer;">${opt}</button>`
    ).join('');
    
    card.innerHTML = `
      <div style="font-weight: 600; margin-bottom: 8px;">🤔 Autopilot needs your input:</div>
      <div style="font-size: 13px; margin-bottom: 10px; line-height: 1.5;">${question}</div>
      <div class="choice-buttons-container">${buttonsHtml}</div>
    `;
    
    thread.appendChild(card);
    thread.scrollTop = thread.scrollHeight;
    
    // Wire up button click handlers
    card.querySelectorAll('.choice-btn').forEach(btn => {
      btn.addEventListener('click', () => {
        const selectedValue = btn.getAttribute('data-val');
        
        // Clean up UI: disable buttons to prevent double-clicks
        card.querySelectorAll('.choice-btn').forEach(b => b.disabled = true);
        btn.style.background = '#10b981'; // Green for selection
        
        // Resolve the promise with the selected value
        resolve({ selection: selectedValue });
      });
    });
    
    // If free text is allowed, listen for the next chatInput submission instead
    if (allowFreeText) {
      // You can wire an event listener to your main text input here as a fallback
    }
  });
}
Inside your runAgentTask execution block, route the tool response like this:
code
JavaScript
const askUserCall = fnCallParts.find(p => p.functionCall.name === 'askUser');
if (askUserCall) {
  const { question, options, allowFreeText } = askUserCall.functionCall.args || {};
  
  // Pause execution and wait for the click
  const userResponse = await awaitUserChoice(question, options, allowFreeText);
  
  // Feed the choice back to Gemini as the tool output
  contents.push({
    role: 'user',
    parts: [{
      functionResponse: {
        name: 'askUser',
        response: { success: true, selectedChoice: userResponse.selection }
      }
    }]
  });
  
  continue; // Skip the rest of the loop and start the next model turn
}
2. Is it possible to make the agent highly capable?
Yes. To transition an agent from simple scripting to handling complex tools like Google AI Studio, Gemini, and NotebookLM, you can implement three key architectural upgrades:
A. Centralize Execution in the Background Service Worker
Extension popups or panels close when focus is lost, which terminates running scripts. To make the agent robust:
The Background Script (background.js) should own the execution loop. It should manage the model calls, state, and file queue.
The Frontend (ai-chat.js) should merely be a UI mirror. It sends the initial task to background.js and receives status updates (e.g., "Step 3 completed") via standard message ports. If the popup closes, the background worker continues automation uninterrupted.
B. Implement Multi-Step Vision Grounding
Dynamic pages often load elements asynchronously, leading to timing issues where the agent clicks a button before the DOM has finished updating.
Implement Visual Verification. After every action (like a click), the background script takes a new screenshot and compares it with the previous step.
If the screenshot is identical, the agent recognizes that the action failed to register (e.g., the menu didn't open) and adjusts its target instead of proceeding blindly.
C. Build a Context-Aware Shadow DOM & iframe Parser
As seen in the errors in your logs, complex Google products make heavy use of nested cross-origin iframes (Word Online, Google Docs editor) and closed shadow roots.
When the agent calls snapshotPage, your background script should recursively inject a content script into all available frames (using chrome.scripting.executeScript with allFrames: true) and stitch them into a single, unified Accessibility Tree.
This allows the model to see inside document viewers and dynamic side panels as if they were part of the top-level webpage.
