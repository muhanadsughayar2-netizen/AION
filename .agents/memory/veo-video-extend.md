---
name: Veo native video extend vs frame-capture continuation
description: How to properly continue/extend a Veo-generated video so audio and motion stay continuous, and why the old approach caused music cuts.
---

Google's Gemini API has a real "extend video" feature for Veo 3.1 / Veo 3.1 Fast only (not Lite, not 3.0, not 2.0): call `generate_videos` again passing the actual previous video object (`instances[0].video = { uri, mimeType }`, from the polled operation's response) instead of an image, with `resolution: '720p'`. Google appends +7 seconds and returns ONE combined, already-stitched video — no client-side joining needed. Limits: input video ≤141s, up to 20 extensions per video, extended video stored 2 days (timer resets each time it's referenced).

**Why this matters:** a naive "continuation" built by capturing the last frame as a static image and generating a brand-new image-to-video clip looks similar to the old ending but is NOT actually continuous — it's two independent generations (each with their own independently-generated music) glued together client-side (canvas + MediaRecorder). That architecture is why music/audio hard-cuts between "extended" segments — there's no way to make two separately-generated audio tracks line up in rhythm, because Google never intended them to connect. Real extend avoids this because Google generates the continuation audio/motion using the actual prior video as context, then stitches server-side.

**Confirmed REST field name (from Google's own "Extending Veo videos" doc, not a guess):** the Python SDK example passes `video=operation.response.generated_videos[0].video` — the entire `Video` object from the prior generation, unmodified. That REST field is `response.generateVideoResponse.generatedSamples[0].video`, an object shaped `{ uri, mimeType }` (a signed `https://generativelanguage.googleapis.com/v1beta/files/...` URL, not a `projects/.../operations/.../generatedVideos/0` resource path). So the correct extend request body is just `instances[0].video = { uri, mimeType }` — the exact same object captured off the original generation's poll response, passed through unchanged. No resource-path construction, no snake_case, no `videoResource`/`resourceName` fields are needed or correct for the Gemini Developer API (those are Vertex-AI-style guesses and were wrong here).

**How to apply:** when building any "continue/extend video" feature that uses Veo, capture `response.generateVideoResponse.generatedSamples[0].video` as-is off the original generation and pass it straight back as `video` on the next `generate_videos`/`predictLongRunning` call — don't rebuild or reshape it. Only offer the feature when the active model is Veo 3.1 or Veo 3.1 Fast. Fall back to frame-capture/image-to-video only for models that don't support native extend. Track cumulative duration and extension count against the docs' caps (141s / 20 extensions).

**Quota trap when guessing an undocumented field name:** Veo's preview `predictLongRunning` extend endpoint allows only a couple of requests per minute. Before finding Google's official doc snippet above, this codebase tried several *speculative* shape guesses (resource paths, snake_case, Vertex-style fields) back-to-back per call, ordering them ahead of the actually-correct shape based on unverified secondhand analysis. That both burned the whole minute's quota on wrong guesses AND meant the real shape was rarely even reached before quota ran out — a wall of 429s that looked like total failure. Lesson: when the exact API field is unclear, search for Google's own docs/SDK examples first rather than reasoning from "likely" REST conventions or secondhand technical writeups — and if guessing is unavoidable, cap attempts per call (2-3 max), delay between them, and set a hard cooldown (~60s) after any 429 shared by both manual retry and any auto-chaining logic.

**Enabling "branching" (extend from any past clip, not just the newest):** if a single mutable global object (e.g. `_lastVideoContext`) tracks "the current scene" and every clip's UI reads that global live, you can never go back and extend an older clip — the global has already moved on. Fix: when rendering each clip's result, take an immutable shallow-copy snapshot of the context *at that moment* and bind that clip's own controls (extend button, custom-prompt input) to the snapshot, not the live global. On extend, build the new scene as a brand-new object (`Object.assign({}, sourceSnapshot, {...changes})`) instead of mutating the source in place, then point the global at the new object. This keeps every past clip independently re-extendable (branchable) while linear/auto-chain features that intentionally want "whatever is newest" keep defaulting to the live global.
